# ADR 0023: Article Inline Media as Attachment Slots

## Status

Accepted — 2026-10-02

Amended — 2026-10-16 (#2687, #2684): the composer no longer uploads at insert time. A file inserted this session is staged in memory under a placeholder author-owned file URI (the length of a real id) and uploaded when the article is published, so nothing reaches public storage before then and a locked article's files never leave the lock. The composer-form contract (an author-owned `pubky://…/files/{id}` destination) and the published form are unchanged; see `docs/data-patterns.md`.

Amended — 2026-10-30 (ADR-0027, `pubky-social-specs` 1.x): the cover leaves the attachment list. A v1 article carries it in its envelope (`cover_image`, a media URI or `null`) and `attachments` holds the inline media alone, so slot 0 is the first inline file. The reader resolves every article through `resolveArticleCover` (`src/libs/post/articleCover.ts`): rule A, an envelope cover is the cover and the slots are the attachments as stored; rule A′, a migrated 0.x article (envelope cover, body references starting at `attachment:1` and none at 0) keeps its shifted slots by reading them as `['', ...attachments]` (removed 2026-11-19, amendment below); rule B, no envelope cover means the 0.x slot-0 rule below. A placeholder staged this session is an author-owned v1 media URI for random bytes (`pubky://{author}/pub/social/v1/files/{hash}.{ext}`). The exception is a locked article: the lock's primary is a v1 post whose envelope cover is `null` and whose slot 0 is the cover, since the unlocked copy renders from the lock's own files (ADR-0022). Rule A′ goes only once no rc.1-written article is left to read: the rc.2 migrator (transform revision 4, pubky/pubky-social-specs#210) renumbers the references and never promotes a referenced or non-image slot 0, so it writes shape A or a null cover and never A′, but its writes are create-only, so a re-walk under revision 4 rewrites no article rc.1 already copied, and neither pinning rc.2 nor raising the revision retires A′; such a tree keeps its shifted references until it is wiped and migrated again. A′ cannot misfire on an app-written article, whose inline references always start at slot 0, nor on a revision-4 copy of a body the 0.x composer wrote, whose first image reference always named slot 1 and is renumbered to slot 0; a hand-written body whose lowest image reference is above slot 1 would read as A′. Amended 2026-11-10: rule B takes `attachments[0]` as the cover only when its file metadata says it is an image, since the fixed migrator leaves `cover_image` null for an article whose slot 0 is not one and Nexus serves every migrated article in the 0.x shape; the cover is image-only. The kind comes from the file row (or a local entry's type), never from the markdown; for v1 media, which Nexus keeps no metadata for, that row is the one `FileNormalizer` synthesizes from the URI's extension. Until a reader has it the slot is a `coverCandidate`: nothing paints as a cover (`usePostArticle` also picks any local cover; a local slot-0 entry index-aligned with the attachments is that slot's metadata and settles it at once), and only an image ever does. The edit composer applies the rule the other way round, for the data's sake: slot 0 stays the cover unless its row says it is not an image, decided once when the attachment strip seeds, so a slow or missing row never costs the article its cover on save. The documented edge is a slot 0 whose read settles with no row (a file Nexus no longer serves, or a failed read): the reader shows no cover, the composer keeps it, so a first content-only save moves that URI into `cover_image`, which rule A then paints provisionally and drops once its row settles the same way; nothing is lost and nothing non-image is ever confirmed as a cover.

Amended — 2026-11-18 (`pubky-social-specs` and `pubky-social-migrator` 1.0.0-rc.2 pinned, `SOCIAL_MIGRATION_TRANSFORM_REV` 4): the migrator the gate runs is the fixed one. It promotes a 0.x article's `attachments[0]` into `cover_image` only when that file is an image and the body does not reference `attachment:0`, and then respells every reference `attachment:{n}` as `attachment:{n-1}`, so its copy is rule A; otherwise it writes a null cover with the attachments as they were, which rule B reads. Its scan is textual and reads plain inline destinations only, so a reference inside a code span or fence counts too (it blocks the promotion when it names slot 0 and is renumbered otherwise), where this app's reader, which walks the markdown tree, sees none; an entity-escaped slot or a reference-style definition, which this app's reader counts, it does not. The 0.x composer wrote none of these. An account whose flag records revision 3 is walked again at the gate, which copies what revision 3 skipped and rewrites nothing, so rule A′ stays (superseded 2026-11-19, amendment below) for the articles rc.1 wrote on test stacks and staging; no production account migrated under rc.1. `src/core/services/homeserver/homeserver.social-migration.test.ts` runs the real migrator over the in-memory homeserver on both 0.x shapes and reads the result through `resolveArticleCover`.

Amended — 2026-11-19 (rule A′ removed): `resolveArticleCover` has two rules. Rule A: an envelope cover is the cover and every `attachment:{n}` indexes `attachments` as stored, whichever slots the body names. Rule B: no envelope cover means the slot-0 rule. The shift that read a body with references but none at slot 0 as `['', ...attachments]` is gone, which supersedes the statements of 2026-10-30 and 2026-11-18 above that A′ stays while an rc.1-written article is left to read. The rule was written for the articles `pubky-social-migrator` 1.0.0-rc.1 copied, and no production account has one: the pinned migrator is rc.2 and no release that carries the migration has shipped. This app's composer cannot write the shape: `serializeArticleBody` numbers a published article's inline media from slot 0 in first-appearance order on every create and every edit, and the offset of 1 is used only for a locked article, whose envelope cover is `null`. rc.2 renumbers the references its textual scan sees, the plain inline destinations (2026-11-18 amendment), and no others. Three kinds of stored article matched the removed rule and read differently now. (1) An article from another client with the cover in the envelope and a lowest reference above slot 0: the rule read it one slot down, and it now reads as stored. (2) An rc.2 copy of a 0.x body whose lowest reference was above slot 1 (the edge the 2026-10-30 amendment names): the same, it now reads as stored. (3) An rc.2 copy of a 0.x article with an image at slot 0 in which a reference is spelled in a way the migrator's scan does not see, a reference-style definition (`[x]: attachment:1`) or an entity-escaped slot (`attachment:&#49;`): rc.2 promotes the cover, renumbers the plain references and leaves each such reference as it was. Now each of those names the file one slot later, one past the end finds no file, and the plain references read as stored, which is right. When every reference is spelled that way the body is unchanged, which is the rc.1 shape, and the removed rule showed the right file for each. In a body that mixes the spellings the removed rule was no repair: it applied only when no renumbered reference named slot 0, and then it read the unseen references right and the renumbered ones one file early (`![a](attachment:2) ![b](attachment:&#49;)` over `[image, f1, f2]` is copied as `![a](attachment:1) ![b](attachment:&#49;)` over `[f1, f2]`; the removed rule read both references as `f1`, and both now read as `f2`). pubky.app never wrote those spellings: `serializeArticleBody` has rejected a hand-typed `attachment:` destination and a reference-style definition of an author file since inline images shipped (#2437), so (3) is a 0.x article another client wrote, and what repairs it is the migrator's scan, not the reader. An article rc.1 copied on a test stack or on staging keeps every reference at its 0.x number, so each one names the file one slot later and the highest one dangles; the edit composer opens it that way, without the dangling reference, and a save would store what it shows. Its cover is unaffected. Only accounts migrated by a pre-release build have an rc.1 copy, and a re-walk under rc.2 does not rewrite it (the migrator's writes are create-only). (3) stays until a migrator whose scan sees those spellings copies the article. A save from the edit composer does not repair it either: a reference-style `attachment:` definition blocks the save, and an entity-escaped reference is saved as the file it now reads.

## Context

Articles (`kind: long`) embed media in their markdown body. PR #2437 introduced inline images with a contract that keeps the body host-agnostic: the composer writes `![alt](pubky://{author}/pub/pubky.app/files/{id})` after uploading at insert time, and publishing rewrites each destination to `![alt](attachment:{n})`, a slot of `post.attachments` (`[cover?, ...inline first-appearance, ...unreferenced originals]`, capped by the spec at 10). Slot 0 is the cover unless the body references `attachment:0`.

Users asked for inline video, audio and PDF. Markdown has no syntax for them, the body never carried a media type, and three places would have to agree on how a slot renders: the rich-text editor (MDXEditor), the markdown-mode textarea and the reader (`react-markdown`). The options were a typed syntax (remark directives such as `::video{src=…}`), a second grammar on links, or keeping image syntax and deciding the kind elsewhere.

## Decision

- **One syntax for every kind.** Images, videos, audio files and PDFs all use markdown image syntax. The published body is `![alt](attachment:{n})` whatever the kind; the composer body is the author's `pubky://…/files/{id}` URI. `serializeArticleBody`, `deserializeArticleBody`, the slot-0 cover rule and the controller contract are unchanged (`src/libs/post/articleInlineMedia.ts`).
- **The kind lives in file metadata, never in the body.** The reader types each slot from `file_details.content_type` (`useAttachmentsMetadata`, matched by `uri`, never by index), a same-session publish from the local files store entry, unlocked (paid) content from the bytes the reader holds, and an external `https:` URL from its file extension. Unknown stays an image, which keeps today's placeholder behaviour; a row of a type the reader has no player for is a placeholder that requests nothing.
- **The ownership invariant is unchanged.** A slot renders only if `attachments[n]` is a file URI owned by the author (a v1 media URI or a 0.x file or blob URI an existing article references); the cover remains image-only.
- **The editor keeps `imagePlugin` for images** and adds a plugin whose import visitor runs ahead of it, claiming only the image-syntax nodes whose file type the composer knows is not an image (session files, the edited post's attachments) or whose `https:` URL has a video/audio/PDF extension. The node exports back to a plain mdast `image`, so the markdown is byte-identical to an image's. An edit holds the editor behind its skeleton until the referenced attachments' metadata has settled, because the import runs once.
- **Caps follow post attachments.** Images keep `IMAGE_MAX_RAW_SIZE`; other kinds the spec's file size limit (`ATTACHMENT_MAX_OTHER_SIZE`). Locked articles keep the lock's own caps.

## Consequences

### Positive ✅

- No change to the persistence contract: articles published before this decision, and other clients that understand `attachment:{n}`, keep working.
- One rewrite pass covers every kind; the serialize-time validation (hand-typed refs, blob URIs, raw HTML, reference-style definitions, the cap) applies to all of them for free.
- The reader degrades safely: a slot whose type is unknown reserves space, then falls back to the image path.

### Negative ❌

- A reader must resolve file metadata before it can tell a video from an image; a cold page shows a skeleton until the rows land.
- Clients that render `![](attachment:n)` as `<img>` without consulting the file type show a broken image for a video. They already needed the attachment list to render anything.

### Neutral ⚠️

- External video/audio/PDF links are classified by extension only; a URL without one renders as an image placeholder.
- Media elements carry no referrer policy, so external sources use `preload="none"` and request nothing until the reader presses play.

## Alternatives Considered

### Alternative 1: remark directives (`::video{src=…}`)

Explicit semantics and a documented MDXEditor plugin. Rejected: enabling `directivesPlugin` re-parses existing article text such as `Note:this` as text directives (import errors or escaped output), the AST lib and the reader would each need a directive parser, and other clients would show the raw directive.

### Alternative 2: link syntax (`[label](attachment:n)`) for non-images

Degrades to a link in foreign renderers. Rejected: link nodes would have to join the slot ordering in the AST lib, the slot-0 rule would need a second node type, and the editor would still need a custom node.

### Alternative 3: CDN URLs or raw `pubky://` URIs in the published body

Rejected in ADR-era discussions of #2437 and unchanged here: host coupling, no ownership check, and a per-render URI parse.

## Implementation Notes

- Reader: `ArticleInlineMedia` routes to `ArticleInlineImage` (unchanged), the `Video`/`Audio` atoms or a PDF card; `PostArticleDetail` resolves the inline slots' rows; each player pauses itself once it leaves the viewport.
- Composer: `inlineMediaPlugin`, `InlineMediaNode`, `InlineMediaEditor`, `MarkdownEditorMediaDialog`; `useInlineMediaUpload` validates per kind and stages the file until the publish (see the amendment under Status); `usePostInput` types the edited post's inline attachments through `useAttachmentsMetadata`.
- Config: `ARTICLE_INLINE_SUPPORTED_MIME_TYPES` (images plus the spec's video, audio and PDF types); the cover list is untouched.
