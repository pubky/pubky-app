# ADR 0025: App-owned grant for same-origin Shop

## Status

Proposed — 2026-10-13, for the App/Shop integration.

## Context

Shop is deployed separately and the SDK can restore the same saved grant on one origin. Loading an external Shop URL in an iframe cannot share the SDK's IndexedDB. The App already owns durable authentication generation, cross-tab synchronization, record retirement, and account switching.

## Decision

Keep `/shop/[[...path]]` in the App. A persistent layout retains App desktop/mobile navigation around a trusted first-party Shop iframe. Proxy the separate Shop deployment at `/shop-embed`, preserving that prefix for HTML, APIs, assets and callbacks. Navigations under this prefix use the App service worker’s network-only route, which consumes navigation preload, and remain outside App offline fallback handling.

App Shop navigation always goes to `/shop`, which maps to `/shop-embed/marketplace`; deeper wrapper paths map to the same suffix under `/shop-embed`. Query strings and fragments survive. An explicit Shop login uses the existing App sign-in page with a validated wrapper-only `returnTo` query, including search/hash; successful Ring, Passport and recovery-file/phrase sign-in returns to that page.

App owns the durable browser history entries for Shop routes. On each same-origin frame document, it adapts client `pushState` calls into child `replaceState` plus one outer push; child replacements remain outer replacements. Outer entries carry an opaque reference to an in-memory snapshot of the frame's document, Next history state and scroll position. Back/Forward within that live document restores the captured state through Next's existing history handler. Scroll restoration waits up to one second for the acknowledged route's local content to fit the saved position, avoiding a clamp against a temporary catalog skeleton. After that deadline the browser clamps to the available page height; user input or another navigation cancels the pending restoration. Keeping the document alive preserves Shop's in-memory catalog search, filters, sort and layout. The adapter reuses captured Next state; it does not manufacture a router tree. Ordinary same-document fragment links use the same outer history ownership and scroll to their target without adding a child-only entry. Modified clicks, downloads, links with another target and clicks already handled by Shop retain their existing behavior.

After App reloads or the iframe is remounted, those document snapshots are unavailable. Back/Forward then replaces the iframe location using the durable outer URL, while stale reports from the old document are ignored until the replacement acknowledges its destination, including redirects. This fallback boots Shop and restores its host session again; it cannot recover catalog state that Shop does not persist. Initial route reports only synchronize the outer URL. The adapter is removed on unmount and reinstalled for each new frame document. While App auth, shared-Link or header search navigation is pending, child route reports are ignored so Next history restoration cannot cancel the host navigation. Link guards start in `onNavigate` and settle through `useLinkStatus`; imperative search uses a React transition. Canceled or completed navigation releases its guard.

The bridge envelope is `{ channel: 'pubky-shop-session', version: 1 }`. Child messages are `ready`, `request-login`, `request-capabilities`, `request-logout`, `request-retry`, and `navigate` with a `path` containing the actual `/shop-embed/...` browser path, search, and hash. The parent accepts only the exact origin and iframe WindowProxy. Unknown fields, versions and request types are rejected. Navigation cannot escape the mount, traverse paths, or target the reserved `/api` and `/_next` namespaces.

The parent's `session` message contains only `snapshot: { generation, shopCleanupEpoch, status, pubky, sessionStoreId, grantId, clientId }`. Status is `ready`, `signed-out`, `restoring`, `temporary-error`, or `reauth-required`. App projects these fields from its existing auth store and subscribes for lifecycle changes, including those synchronized from other tabs. Empty generation is possible before the first durable transition. Temporary failure preserves the reference; a record is usable only in `ready`. No serialized session, bearer, proof key or cookie export crosses the bridge.

App remains the sole owner of the shared App grant's creation, replacement and retirement. Shop restores the exact public reference, verifies pubky/client/grant identity and effective capabilities, cancels stale work when the generation changes, and never deletes an App-owned grant. Same-origin code shares the origin's trust boundary; the iframe is not an isolation boundary. It is intentionally unsandboxed so asynchronous payment redirects can navigate the top window after transient user activation has expired.

New Ring/Bitkit and Passport approvals add `/pub/paykit/:rw`, `/priv/pubky.app/:rw`, `/pub/chat/v0/:rw` and `/priv/chat/v0/:rw` to App/Locks permissions. Recovery-key sign-in and browser signup obtain root storage grants (`/:rw`). Shop accepts existing grants that cover its core storage scopes without Chat access. The replacement Chat consumer and its permission-upgrade handling belong to Shop #209 and are not implemented by this integration.

Older grants missing core Shop access request the fixed Shop scopes through `AuthController.requestCapabilities` and the existing Ring approval panel. The dialog also offers Passport or recovery-key sign-in for users without Ring. Explicit sign-in carries a `shopReauth` marker containing the current host generation. Only Shop's validated return URL and matching generation permit an authenticated user to stay on sign-in. Ring/Bitkit, Passport and recovery-file/phrase reauthorization are bound to the current App identity, so a different key cannot replace the account or discard its unbacked recovery material. The existing grant remains intact until approval; a newly adopted generation expires the exception and returns to Shop. This also handles a child that cannot restore an SDK record while App still has a live handle. Child messages cannot pick scopes or an account. Ready/subscription events do not initiate login or approval; explicit child requests open App UI. Opening Ring still requires a direct click in the parent. Encryption-key permission `e`, marketplace service approval and Locks seller connection remain separate contracts.

### Logout and private Shop cleanup

Embedded logout goes through App's existing backup-aware sign-out hook. A pending recovery-key backup only opens the logout page; no credential cleanup or epoch rotation occurs until logout is confirmed there.

App atomically persists the optional public `shopCleanupEpoch` in `auth-store-v3.state` when the identity changes (including logout and same-account logout/login), before removing local credentials. Same-account grant refreshes retain the previous epoch, including an absent legacy epoch. Only an identity boundary initializes or rotates it. Legacy records/snapshots default to an empty epoch. Shop keeps `shop-host-cleanup-epoch-v1`; a missing marker, including for the empty legacy epoch, requires cleanup before restoring the host grant. The marker is acknowledged only after successful cleanup. This makes an absent/unmounted iframe and interrupted cleanup recoverable. Shop compares the latest durable host generation, identity and epoch before restoring or acknowledging, and fences in-flight work immediately when the host leaves ready state. `request-retry` explicitly retries a temporary host restore without opening sign-in; frame load and ready handshakes republish the current lifecycle state.

After a successful durable logout commit, App's controller delegates bounded, best-effort immediate cleanup through AuthApplication to ShopEmbedService, independently of an iframe. Both apps serialize cleanup/host restore with `pubky-shop-host-cleanup`; Shop may nest its own auth finalization lock, which App never acquires. If Web Locks are unavailable, App leaves the durable epoch pending rather than starting unfenced cleanup. App skips epochs already acknowledged by Shop unless key teardown remains pending. It retries pending cleanup on startup/network return only while still signed out, and rechecks the durable generation/epoch before clearing stored data. No delayed logout cleanup may erase a new login. If the logout commit itself fails, App's tab-only sign-out fallback cannot publish a new cleanup epoch or promise cross-tab Shop cleanup.

Embedded deployments use the Shop database namespace `shop-franky` and keyring `shop-franky-messaging-keyring`. App clears only the explicit Shop private-table allowlist, preserving public caches and device-local `commerce_delivery_addresses` (Shop ADR 0019). Under the existing `pubky-messaging-keys` fence, wrapped tables are cleared before the keyring’s `wrapping-key` and `wrapping-key-epoch` records. The durable `pubky-messaging-keys-teardown-pending` marker stays until teardown succeeds. The allowlist includes the replacement Chat tables (`chat_identity`, `chat_conversations`, `chat_messages`, `chat_sync_state`) for compatibility with that consumer; their inclusion does not establish working Chat integration. Missing databases/stores are not created or upgraded. A blocked/offline cleanup is bounded and leaves the epoch pending for Shop's next bootstrap.

`ShopEmbedService` removes only Shop's service credential keys (`pubky.marketplace.session.v1`, `pubky.marketplace.inventory-session.v1`, `pubky.marketplace.locks-frontend-session.v1`, `pubky.messaging.session.v1`, `shop-chat-inbox-session:v1`) and calls the existing same-origin `DELETE /shop-embed/api/marketplace/session` to unpair the current BFF session/flow. Before removing the marketplace session records (`pubky.marketplace.session.v1`, `pubky.marketplace.inventory-session.v1`) it reads them and revokes each distinct, unexpired bearer at the transaction service (`DELETE /v1/auth/sessions/{id}`, `keepalive`, origin from `PUBKY_RUNTIME_MARKETPLACE_URL`), because the service keeps a session valid until its TTL unless it is revoked and the Studio bearer exists nowhere but `localStorage` when no Shop frame is loaded. This BFF is Shop's Next.js server route layer, which owns its HttpOnly session and flow cookies. The cleanup service preserves Shop's owned-grant pointer and retirement queues and does not remove App SDK records; App's auth controller separately retires its outgoing grant. Shop owns retiring any prior standalone Shop grant and clearing its active in-memory credentials. Custom Shop database names require updating this shared deployment contract before deploying the pair.

## Consequences

Deploy compatible App and Shop builds with the same-origin proxy and Shop's BFF together. There is no enable flag or external fallback. Shop validates its embedded BFF configuration at startup; deployment verification must also check the no-store `/shop-embed/api/marketplace/health` endpoint before promotion. App uses that endpoint to detect BFF outages and restores Shop automatically when it recovers. Before the iframe loads, a failed check can show unavailable immediately; a loaded frame is preserved until three consecutive online checks fail, at least 10 seconds apart. Success resets the count; offline or hidden intervals pause polling and reset it, so network interruptions and payment-app returns do not immediately discard the running frame. This readiness check does not prove a real signer or payment flow. The App must trust the Shop deployment as first-party code, preserve runtime client identity, and configure backend origins/issuer trust for the App origin. See [Shop deployment instructions](../shop-embedding.md). Real signer, Safari storage and payment-return verification require the deployed pair and remain release checks.

## Alternatives

- **Keep Shop on a separate origin:** cannot share the App's SDK IndexedDB session or provide the integrated App shell.
- **Let Shop own a second grant on the shared origin:** avoids sharing the App's saved reference, but duplicates approval, account switching and retirement responsibilities. App ownership keeps one homeserver session lifecycle.
- **Merge Shop into the App build:** removes the iframe and proxy boundary, but couples both release cycles. The same-origin proxy preserves separate frontend deployments.
